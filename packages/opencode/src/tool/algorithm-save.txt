Use this tool to save a trading algorithm to Finny's local storage. Every saved algorithm is validated first — the save is blocked unless the strategy passes Finny's strict validator.

## When to Use
- After generating a new trading algorithm (strategy.py, config.json, backtest.py)
- After modifying an existing algorithm
- When the user asks to save their current algorithm

## Parameters
- **name** (required): A short, descriptive name for the algorithm (e.g., "momentum-spy", "mean-reversion-eth", "breakout-qqq"). Use kebab-case.
- **code** (required): The full strategy.py source code
- **saveMode** (required): Either `"new"` or `"version"`. There is no default — you must choose every time. See **Choosing saveMode** below.
- **docsMode**: Required with `saveMode: "version"`. Use `"inherit"` to snapshot the prior mission/preferences/risk unchanged, or `"replace"` to provide replacements. Decisions are append-only in either mode.
- **language**: Programming language, defaults to "python"
- **description**: A brief human-readable summary of what the strategy does
- **config**: The config.json content as a string. For new algorithms this must include `symbol`, `asset_class`, `interval`, `required_history_bars`, and non-empty strategy knobs under `params`. The validator cross-references every strategy param against the strategy code, so do not declare params you do not use.
- Finny generates the trusted strict-v2 backtest runner internally. Do not provide custom runner code.
- **reasoning**: Markdown explaining why this version exists — what hypothesis it tests, what changed from the prior version and why. Written to `reasoning.md` inside the version directory. ALWAYS provide this on every save.
- **mission**: WHO: hypothesis, scope, exit conditions, and the machine-enforced risk contract. Required for new algorithms and `docsMode: "replace"`. Must be valid `schema_version: 4` with all Core 8 questionnaire records plus `risk_contract` (`sizing_stop_distance_pct`, `protective_stop.mode`, `drawdown.mode`, `drawdown.limit_pct`, and `max_positions`). `engine_stop` is reserved and currently fails closed; use `strategy_next_open` only when the strategy contains validator-verifiable stop logic.
- **prefs**: HOW: sizing, risk, constraints, interval, asset. Included in each version snapshot.
- **decisions**: New design-decision entries. Existing decisions are preserved and these entries are appended.
- **riskContract**: JSON risk contract saved as `risk.json` in each version.

## Mission YAML Safety

Mission frontmatter is parsed as strict YAML before save. Any prose that may
contain `:`, `#`, `{}`, `[]`, commas, or multiple sentences must use a block
scalar (`|` or `>-`) instead of an inline value. Use block scalars for
`hypothesis`, `strategy.entry_signal`, `strategy.risk_profile`,
`strategy.success_metric`, `exit_conditions`, and long questionnaire answers.
Never write colon-bearing prose like `Strategy adapts: enters...` on the same
line as a YAML key.
Use these exact Core 8 `questionnaire[].id` values once each and no others:
`market_universe`, `timeframe_bar_interval`, `strategy_family`,
`directional_thesis_regime`, `entry_signal_idea`,
`exit_invalidation_rules`, `risk_tolerance_max_drawdown`,
`backtest_window_success_metric`.

## Choosing saveMode

You MUST decide explicitly. Versions cannot be split apart later — getting this wrong has frustrated real users.

- Use `saveMode: "version"` when the user is **iterating on an existing algorithm** — improving it, adding features, fixing bugs, tweaking parameters, or refining the logic. Key signals: "improve X", "add stop-loss to X", "update X", "fix X", "make X better", or any prompt that references a specific existing algorithm by name. The new save will be saved as v(N+1) of the existing algorithm, and v1..vN remain available in the version history.
- Use `saveMode: "new"` when the user wants a **separate, independent algorithm** — a different strategy concept, a different asset, or when they explicitly say "build a new", "create another", or "make a separate". The new save creates a sibling algorithm that lives alongside the original.
- **When in doubt, prefer `"version"` if the user references an existing algorithm.** Users expect "improve my algo" to update the existing one, not create a duplicate with a slightly different name. Only use `"new"` when it's clearly a distinct strategy.

If you pass `saveMode: "new"` and the name is already taken, the tool returns an error with a suggested alternative name — do NOT retry with the same name.

If you pass `saveMode: "version"` and no algorithm with that name exists yet, the tool returns an error — switch to `saveMode: "new"`.

## Directory Layout (on disk)
Each algorithm is stored under `$FINNY_HOME/algorithms/<id>/` with this structure:
```
<algorithmId>/
  meta.json               ← internal metadata (do not reference)
  mission.md              ← WHO: hypothesis, scope, exit conditions
  prefs.md                ← HOW: sizing, risk, constraints
  decisions.md            ← HUMAN log: material design decisions
  memory.md               ← AGENT log: written on /compact only
  CURRENT                 ← pointer to active version (e.g. "v01")
  data/                   ← OWNED BY SUB-AGENTS (read-only for you)
  v01/
    strategy.py           ← the algorithm code
    config.json           ← config parameters
    mission.md            ← immutable mission snapshot
    prefs.md              ← immutable preferences snapshot
    decisions.md          ← append-only decisions snapshot
    risk.json             ← immutable risk-contract snapshot
    backtest.py           ← custom backtest runner (if any)
    reasoning.md          ← why this version exists
  v02/ ...
```

Root `mission.md`, `prefs.md`, `decisions.md`, and `risk.json` are compatibility mirrors of `CURRENT`; the version directory is authoritative. The pointer advances only after the complete new version has been written.

## Behavior
- On success: a new row is inserted. With `saveMode: "new"` the algorithm starts at version 1 with status "draft". With `saveMode: "version"` the version is incremented and the lineage's status is preserved.
- Old versions are NOT deleted — every save adds to the history. Users can list versions with `finny_algorithm_versions` and export a specific version with `finny_algorithm_export`.
- If validation fails, the save is rejected and you receive a structured list of errors. The attempt does NOT count towards the algorithm's version — version only advances on successful saves.
- If a new algorithm is missing required execution config, the save is blocked. Do not save first and patch missing `symbol`, `asset_class`, `interval`, `required_history_bars`, or `params` with `finny_algorithm_set_params`.

## Retry Protocol (MANDATORY)

The validator may reject your first attempt. When the tool returns `metadata.retry === true`, follow these rules:

1. **Do NOT apologise to the user.** The retry output is marked `transient: true` and suppressed from the user's chat. Any text you write in the same turn will also be suppressed.
2. **Do NOT narrate the fix.** Just rewrite the entire strategy, correcting every listed error, and call `finny_algorithm_save` again with the same `name` and the corrected code.
3. **You have 3 attempts total.** After the 3rd rejection the tool returns `metadata.exhausted === true` and a user-visible error — at that point, ask the user for more specifics, do not silently retry.
4. **Version stability:** because Finny only increments the version on successful saves, repeated rejected attempts all stay at the same version. Your job during retries is simply to produce code that passes — nothing else is visible to the user.

## Validator Pitfalls (avoid these on the first attempt)

- **State must live on `self`.** Never write `losses = deque(...)` inside `on_bar` — that deque is recreated every bar and loses history. Use `self.losses = deque(maxlen=...)` in `__init__`.
- **Use `bar["open"]` for decisions and `bar["prev_close"]` / history for indicators.** Current-bar close/high/low are not decision-time-safe.
- **Every `config.json` key must be referenced in the strategy.** If you declare `max_risk_per_trade_percent`, the strategy must use it — either read it at init time or match the attribute name.
- **Standard deviation, not RMS.** `sqrt(sum(x**2)/N)` is wrong. Subtract the mean: `sqrt(sum((x - mean)**2)/(N-1))`.
- **RSI edge cases:** when both `avg_gain == 0` and `avg_loss == 0` (flat market), return RSI = 50 (neutral), NOT 100. Otherwise a flat market triggers spurious SELLs.
- **Size positions.** `self.position = 1` with no sizing math silently bets full equity. Use `qty = equity * risk_pct / stop_distance` or similar.

## Important
- ALWAYS save after generating an algorithm. Do not skip this step.
- Use clear, descriptive names that indicate the strategy type and target asset.
- Include the description so users can identify their algorithms later.
